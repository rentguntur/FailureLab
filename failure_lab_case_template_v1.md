# Failure Lab — Master Case Template v1.2

## Core principle
Failure Lab is not a collection of failure stories. It is a system for learning:
**promise → reality → warning signals → decisions → reinforcing failure mechanism → intervention window → tomorrow's checks.**

## Mandatory case structure
1. Business at a glance
2. See the business — 3–5 real, attributable images
3. Business Model Flow
4. Why it looked promising
5. Evidence-backed timeline
6. Money Journey
7. Financial / operating deterioration
8. Case-specific Economics / Failure Trap visual
9. Failure Chain
10. Why growth did or did not help
11. Warning Signals
12. Decision Gates
13. Early-Warning Loop
14. Management Intervention Windows
15. Could it have been saved?
16. Who should have acted?
17. Stakeholder Impact
18. Final Failure Tree
19. Tomorrow Test
20. Practical Checklist / Tool
21. Current Status
22. Evidence / Sources

## Evidence rules
- Freeze the event before explaining causes.
- Build the timeline before assigning causality.
- Prefer regulatory, court, insolvency, audited/company records, contemporaneous statements and strong contemporaneous reporting.
- Separate: verified fact / company-founder explanation / independent reporting / academic interpretation / Failure Lab analysis / counterfactual.
- Distinguish event, impact, contributing condition, root-cause hypothesis, proximate cause and terminal event.
- Test competing explanations when possible.
- Never turn hindsight into fact.
- State uncertainty when evidence cannot resolve it.
- Check current legal/operating status where relevant.

## Numbers rules
For every important number: define the metric, date/period, source and cost/revenue boundary.
If sources conflict, do not silently choose the biggest number. Reconcile them, label claims, prefer stronger contemporaneous evidence, or use a range/directional statement.

## Economics rules
Name the smallest useful unit: order, customer, store, flight, project, shipment, vehicle, etc.
Show the relevant revenue and cost boundary.
Growth, funding, valuation, revenue and order count are not proof of business health.

## Visual rules
Normally include:
- 3–5 real contextual images
- Business Model Flow
- 1 case-specific causal/economics visual
- Failure Chain or Failure Tree
- timeline
- financial/operating visual when meaningful
- Early-Warning Loop

Do not add visuals merely for decoration. Do not use generic PowerPoint diagrams. Each visual must make an important idea faster to understand.

## Editorial rules
Simple, friendly, conversational English. Short sentences. Curious and practical.
Avoid MBA language, unnecessary jargon, robotic phrasing, clichés and hindsight blame.
Do not overstuff a case.

## Failure-pattern tags
Use 1–3 dominant patterns:
negative unit economics, premature scaling, liquidity/cash flow, debt spiral, working capital, customer concentration, founder conflict, governance, strategy/positioning, product-market mismatch, operational complexity, quality, supply chain, regulatory/legal, capital allocation, acquisition/integration, competition, market timing, external shock, fraud/misconduct where evidenced.

## Intervention rules
For each intervention window ask:
- What was known then?
- What could reasonably have been done then?
- What evidence supports that?
- What is our counterfactual analysis?
Never claim a hypothetical intervention definitely would have saved the business.

## Lessons locked from Dunzo + PepperTap
1. Explain the business before explaining the failure.
2. Real photos provide context; diagrams should explain mechanisms.
3. Every case needs a case-specific causal/economics visual.
4. A failure chain must explain HOW the problem grew.
5. “Ran out of money” is usually an outcome, not the root cause.
6. Never automatically blame debt, funding, competition or growth.
7. Unit economics must define the unit and cost boundary.
8. Conflicting numbers must be surfaced, not silently resolved.
9. Founder/company claims must remain labelled.
10. Distinguish business-model failure from the later legal/operational outcome.
11. Do not describe a pivot as if the whole company simply disappeared.
12. Counterfactuals must be labelled as analysis.
13. Keep the page lean; add content only when it teaches something.
14. Keep CSS/components clean and reusable; never layer conflicting case-specific CSS.
15. Use the library to teach different failure patterns, not repeat the same startup story.
16. Every warning signal should lead to a possible action, owner or decision.
17. Every case ends with a practical Tomorrow Test.
18. After every 2–3 cases, compare patterns and improve the tool/checklist layer.

## Freeze Gate
A case is frozen only when:
- business is understandable
- images are sourced/attributed
- flows and diagrams work
- timeline and numbers are evidence-backed
- economics are defined
- causal mechanism is clear
- warning signals are measurable/actionable
- counterfactuals are labelled
- current status is accurate where relevant
- Tomorrow Test is practical
- source conflicts are disclosed
- unsupported causal claims are removed
- desktop/mobile layout is checked
- CSS has no regressions
- homepage entry is ready
